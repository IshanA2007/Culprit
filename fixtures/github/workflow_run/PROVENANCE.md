# Deploy feed — `workflow_run` fixtures (provenance)

These 22 fixtures are the **GitHub deploy-feed** half of the Milestone-2 ingest
contract — the mirror image of `fixtures/sentry/{event_alert,issue}/`. Each is
one `workflow_run` webhook (the "AWS Deployment" that shipped a recorded run's
window), in the recorder envelope format (`received_at`, `source`, `resource`,
`headers`, `raw_body`). One fixture per run in `runs/`, linked by that run's
`deploy:` field. Generated by `harness/deployfeed.py`
(`culprit-harness backfill-deploys`).

## How they were produced

M1 deferred the live GitHub recording (no ngrok/live recorder in the recording
session). Rather than hand-invent payloads, these are **reconstructed from real
data**:

| Part of the payload | Source | Real? |
|---|---|---|
| Field **schema** (every key/type of `workflow_run`) | a real upstream production "AWS Deployment" run — `harness/deployfeed_inputs/template_upstream.json` (from `thecourseforum/theCourseForum2`) | ✅ real; parity enforced by `tests/test_deployfeed.py` |
| `workflow_run.head_sha` / `head_commit` | the run's real `release_sha`, resolvable on the fork; commit metadata from the fork | ✅ real |
| `repository` / `head_repository` / `sender` | the real fork repo + owner objects (`fork_repo.json`, `owner.json`) | ✅ real |
| `event` = `workflow_run` | the real "AWS Deployment" is chained off CI, so its own event is `workflow_run` | ✅ real semantics |
| ids (`id`, `node_id`, `run_number`, `x-github-delivery`) | synthesized **deterministically** from the run id | ⚠️ synthetic, no external referent |
| timestamps (`run_started_at`/`updated_at`) | derived from the run's `injected_at` + the real template's deploy duration (492 s) | ⚠️ harness-derived |

## Field deltas from a live GitHub delivery (documented honestly)

- **`head_branch` = `master`** — normalized to the production deploy branch. It is
  deliberately **not** the internal `fault/<id>-<ts>` branch: the deploy feed must
  never name the culprit (anti-leakage). The `release_sha` itself is resolvable on
  the fork via the retained window tags.
- **`x-hub-signature-256` — signed with the fork's real GitHub webhook secret.**
  The payload *content* is reconstructed (stamped `"reconstructed": true`), not a
  raw GitHub delivery. But the secret is a **genuine** GitHub webhook secret: a live
  `workflow_run` webhook was configured on the fork (`IshanA2007/theCourseForum2`)
  and GitHub was confirmed delivering genuine events to it — verified live
  (deliveries `requested` → `in_progress` → `completed`, 2026-07-04T16:55Z) — then
  the temporary webhook was torn down. These fixtures are signed with that same
  `CULPRIT_GH_WEBHOOK_SECRET` (env-injected, never committed), so the HMAC verifies
  exactly as a real delivery would — the GitHub parallel of the Sentry fixtures
  verifying against `SENTRY_CLIENT_SECRET`
  (`tests/test_corpus.py::test_deploy_webhook_signatures_verify`). Regenerating the
  signed corpus therefore requires `CULPRIT_GH_WEBHOOK_SECRET` in the environment.
- **`conclusion` = `success`** — the deploy succeeds; the injected fault is a code
  commit *within* the shipped window, not a failed deploy.

## To record these live instead

Add `harness/fork/fake-deploy.yml` to the fork's master, enable the fork's
(dormant) Actions, point a webhook at the recorder, and merge a window to master.
`fake-deploy.yml` mirrors the real aws.yml trigger so live payloads carry the same
`event: workflow_run` / `head_branch: master`.
